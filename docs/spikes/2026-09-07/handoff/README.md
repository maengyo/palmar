# 스파이크 G — 데몬 핸드오프를 실제로 만들어 본다 (2026-09-07 저녁, #19)

스파이크 A 는 fd 하나가 넘어가는 것만 봤다. 여기서는 **클라이언트가 붙어 있는 채로 데몬을 통째로
교체**한다. `⑦` 에서 (a) 핸드오프를 고를 수 있는지가 아래 셋에 달렸다.

1. **바이트를 잃는가** — pane 이 `SEQ 1`, `SEQ 2` … 를 찍고 클라이언트가 구멍을 센다.
2. **얼마나 끊기는가** — 마지막 바이트 → 교체 → 첫 바이트.
3. **코드가 얼마나 드는가.**

```sh
python3 handoff.py run           # 느린 pane (5ms 간격)
python3 handoff.py run --fast    # 최대 출력
```

## 넘기는 것

```
daemon1 ──socket.send_fds──▶ daemon2
          [ PTY master fd ]        SCM_RIGHTS
          [ pane 상태 JSON ]       pid · produced(절대 오프셋)
          [ 링버퍼 바이트 ]         1MB, 셸 pane 기준(스파이크 F)
```

클라이언트는 **자기가 어디까지 받았는지**를 알고 있다가 `ATTACH 0 <offset>` 으로 다시 붙는다.
새 데몬이 그 지점부터 링버퍼를 재생한다. 절대 오프셋을 같이 넘기는 것이 핵심이다 —
링버퍼만 넘기면 어디부터 재생할지 모른다.

## 결과 (각 6초 창, 교체는 3초 지점)

| 조건 | 실행 | 순번 | 구멍 | 끊김 |
|---|---|---|---|---|
| 느린 pane (5ms 간격) | 5회 | 637~646개 | **0** | 52 · 55 · 55 · 67 · 71 ms |
| **최대 출력** | 3회 | **113만 개** | **0** | 27 · 29 · 30 ms |

**바이트를 안 잃는다.** 최대 출력에서 1,130,280개가 연속이었다(`hi - lo + 1` 과 정확히 일치).
느린 쪽도 5회 다 구멍 0.

**끊김은 30~70ms.** 최대 출력일 때가 오히려 짧은데, 재접속 직후 보낼 것이 이미 쌓여 있어
첫 바이트가 곧바로 오기 때문으로 보인다(추정이다).

**pane 은 교체를 모른다.** 로그가 그대로 보여 준다 — daemon1 이 `produced=3060` 까지 읽고 넘기면,
daemon2 가 같은 pid(2164)의 fd 를 이어받아 `produced=3060` 부터 계속한다.

```
[daemon1] client attached from 0, replayed 615B
[daemon1] handoff requested
[daemon2] inherited fd=3 produced=3060 ring=3060B (state said 3060B)
[daemon1] handed off, exiting
[daemon2] client attached from 3060, replayed 36B
```

## 코드량

| | 줄 |
|---|---|
| 파일 전체 (주석·빈 줄 포함) | 284 |
| 코드만 | 234 |
| **핸드오프 자체** (넘기기 + 받기 + 재개) | **32** |

핸드오프는 **32줄**이다. 다만 이 값이 싼 이유는 나머지가 이미 그 모양으로 짜여 있기 때문이다 —
`Pane` 이 절대 오프셋과 링버퍼를 들고 있고, 클라이언트가 오프셋으로 재개하는 프로토콜을 쓴다.
**그렇게 안 짜 두면 32줄이 아니다.** 이게 이 스파이크의 진짜 결론이다: 핸드오프는 나중에 붙이는
기능이 아니라 **처음부터 그 모양으로 짜는 것**이다.

## 걸린 것

**새 데몬이 부모의 stdio 를 물려받는다.** 첫 실행에서 `python3 handoff.py run | tail` 이 안 끝났다.
daemon2 가 stdout 파이프를 들고 있어 `tail` 이 EOF 를 못 본 것이다. **제품에서는 새 데몬이 stdio 를
떼야 한다** — 안 그러면 palmer 를 띄운 터미널이 안 닫힌다.

## 안 잰 것

- **pane 여러 개.** 하나만 넘겼다. fd 여러 개를 한 번에 보내는 것은 `SCM_RIGHTS` 가 지원하지만
  안 해 봤고, 링버퍼가 pane 수만큼 늘면 메시지 크기가 문제 될 수 있다(지금은 4MB 로 받는다).
- **클라이언트 여러 개.** 하나만 붙였다.
- **에이전트 pane.** `sh` 루프로만 쟀다. `claude` 를 넘기면 SIGWINCH 흔들기(스파이크 F)와 어떻게
  맞물리는지 안 봤다.
- **웹소켓이 아니다.** 재개 프로토콜을 보려고 TCP 줄 단위로 했다. 웹소켓은 스파이크 D 에 있다.
- **크래시.** 정상 교체만 했다. daemon1 이 갑자기 죽으면 fd 가 닫히고 pane 은 SIGHUP 을 받는다
  (스파이크 A 의 반대 사실). **핸드오프는 업데이트를 위한 것이지 크래시 대비가 아니다.**
- **Linux.** macOS 에서만 쟀다.
