# ⑨ 의 남은 질문 — 링버퍼를 pane 당 얼마나 들 것인가 (2026-09-07)

스파이크 F 가 **에이전트는 SIGWINCH 로, 셸은 바이트 재생으로** 되살린다는 것을 정했다.
남은 것은 크기 하나다. `ringsize.py` 와 `altwaste.py` 로 쟀다.

## 1. 실제 출력이 줄당 몇 바이트인가 (`ringsize.py`)

| 무엇 | 바이트 | 줄 | 줄당 |
|---|---|---|---|
| `git log --oneline -100` | 1,855 | 20 | 93 |
| `ls -la /usr/bin` | 58,473 | 918 | 64 |
| 색 있는 빌드 로그 200줄 | 6,892 | 200 | 34 |
| **`git diff --color`** | 2,283 | 9 | **254** ← 최악 |
| python 역추적 40회 | 3,640 | 120 | 30 |

평균 95B/줄, 최악 254B/줄. **최악으로 잡으면 256KB = 약 1,000줄 = 30줄 화면 34개.**

## 2. 예상이 틀렸다 — alt-screen 은 비싸지 않다 (`altwaste.py`)

"alt-screen TUI 는 화면을 계속 다시 그리니 버퍼를 순식간에 채울 것" 이라고 예상하고 쟀는데
**반대였다.**

| 무엇 | 초당 | 256KB 가 차는 데 |
|---|---|---|
| **`top` (진짜 alt-screen)** | **1,064B** | 246초 |
| `top -l` (alt-screen 아님, 화면을 계속 찍음) | 254,526B | **1.0초** |
| 셸 + 보통 명령 | 250B | 1,048초 |

**alt-screen 은 커서로 바뀐 곳만 고치므로 오히려 싸다.** 버퍼를 순식간에 채우는 것은
alt-screen 이 아니라 **출력량이 많은 아무 프로그램**이다 — 빌드 로그, `yes`, `top -l`.

그러니 **alt-screen pane 에서 버퍼를 안 키우는 이유는 용량이 아니라 쓸모다** — 재생해도 화면이
안 만들어진다(스파이크 F). 크기 걱정과는 별개의 이유다.

## 정하는 값

- **pane 당 256KB.** 최악 출력에서도 1,000줄, 보통이면 2,700줄이다. pane 16개면 4MB —
  데몬 유휴 RSS 25.6MB 위에 얹어도 감당된다.
- **alt-screen 에 들어가면 버퍼를 안 키운다.** `ESC[?1049h` 로 들어가고 `ESC[?1049l` 로 나오는
  것을 스트림에서 본다(스파이크 F 에서 이미 이 방법으로 탐지했다). 들어가기 전 바이트는 남겨 둔다 —
  나오면 셸 스크롤백이 이어져야 한다.
- **재접속 때:** alt-screen 이면 SIGWINCH 흔들기, 아니면 버퍼 재생.

## 안 잰 것

- 사람이 위로 얼마나 스크롤해 보고 싶어 하는지. 256KB 는 "충분해 보이는" 값이지 관찰이 아니다.
- 링버퍼를 디스크로 넘기는 길. 지금은 메모리만 본다.
- pane 이 20개를 넘을 때. 16개까지만 계산했다.
