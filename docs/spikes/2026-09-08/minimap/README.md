# 스파이크 J — 미니맵이 무거운가 (2026-09-08)

사용자가 **캔버스를 무한히 자라게** 하기로 정했다(불편은 사용자 몫). 그러면 밀려난 창을 찾을
방법이 필요하고, **미니맵으로 지금 보고 있는 자리를 보여 주자**는 요구가 나왔다. 무거워지는가.

## 걱정한 것

미니맵 자체는 사각형 N개다 — 그건 공짜다. 위험한 것은 **스크롤마다 다시 그리는 것**이다.
스크롤 이벤트는 초당 수십 번 오고, 거기서 DOM 레이아웃을 읽으면(`offsetLeft` 등) 강제 재계산이 난다.
**cate 가 줌 값을 창마다 prop 으로 내려 초당 374번 다시 그린 것이 이 종류다**(`AGENTS.md` 금지 항목).

## 어떻게 쟀나

6000×4000 캔버스에 창 N개를 놓고 **8ms마다 스크롤을 자동 왕복**시킨다(사람이 끄는 것보다 빡세다).
`requestAnimationFrame` 으로 프레임 시간, Long Task API 로 긴 작업을 센다. 6초 창, 각 1회.

- `none` — 미니맵 없음 (기준선)
- `transform` — 위치를 **우리가 아는 값**으로만 계산하고 뷰포트 표시는 `transform` 하나만 바꾼다(합성만)
- `layout` — **틀린 길**: 스크롤마다 DOM 에서 `offsetLeft/offsetTop` 을 읽고 `left/top` 을 쓴다

## 결과 (Chrome 헤드리스, M 계열 맥, 각 1회)

| | fps | p50 | p95 | 최악 | 긴 작업 | 스크롤 이벤트 |
|---|---|---|---|---|---|---|
| 미니맵 없음 · pane 16 | 60.0 | 16.7ms | 16.7ms | 16.8ms | 0 | 0 |
| **transform · pane 16** | 60.0 | 16.7ms | 16.8ms | 16.8ms | 0 | 360 |
| layout · pane 16 | 60.0 | 16.7ms | 16.7ms | 16.8ms | 0 | 360 |
| **transform · pane 40** | 60.0 | 16.7ms | 16.7ms | 16.8ms | 0 | 360 |
| layout · pane 40 | 60.0 | 16.7ms | 16.7ms | 16.8ms | 0 | 360 |

**안 무겁다.** 미니맵이 있든 없든 프레임 시간이 구분되지 않는다.
**걱정했던 "틀린 길" 도 안 아팠다** — pane 40개에서 레이아웃을 매 스크롤 읽어도 60fps 였다.
사각형 40개 읽는 것은 브라우저에 아무것도 아니다.

## 그래도 `transform` 으로 만든다

성능 때문이 아니라 규칙 때문이다. `AGENTS.md` 가 "창마다 값을 내리지 마라, 스토어에서 직접 읽어라"
라고 하고, **위치를 이미 아는데 DOM 에 다시 물어볼 이유가 없다.** pane 100개나 느린 기계에서는
갈릴 수 있고 그건 안 쟀다.

## 안 잰 것

- **빈 사각형으로 쟀다.** 실제로는 xterm 40개가 같이 돌면서 스크롤한다. 이게 가장 큰 구멍이다.
- 헤드리스라 **WebGL 없이** 쟀다(DOM 렌더러).
- M 계열 맥 1회. 통합 GPU 리눅스·윈도우는 #21.
- pane 100개 이상. 미니맵 사각형이 그때도 싼지는 모른다.
